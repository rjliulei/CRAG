## 1) rag_worse 最该被什么信号抓住（可计算、不看 gold）

1. **闭卷–检索冲突**：同题先出短闭卷草稿 `a0`，再看 top 片段是否支持 `a0`；检索高分但与 `a0` 实体/数值/集合边界冲突 → **检索在害人**。
2. **问题约束覆盖不足**：从 query 抽槽（年份、实体、集合类型），算 top-k 对槽的覆盖比例 `c`；`c` 低却硬走 RAG → 典型过度检索。
3. **跨片段约束互斥**：多个高分 chunk 在关键槽上互相打架 → 不可信证据，应缩窗/弃检索而非合并列举。
4. **检索相对闭卷的大改且无支撑**：RAG 方向相对 `a0` 改动大，且 top 句对改动点缺乏支持 → 「被噪声带偏」。
5. **（辅助，不作主信号）query–chunk max 余弦**：v1 已证几乎不触发（中位≈0.75），**不能**当主判据。

- **机制**：约束槽 → `c`；短闭卷 `a0`；`c` 极低→拒答/闭卷；`a0` 与检索冲突→**输出 a0**；否则检索生成。  
- **为何打 rag_worse**：过度检索绑架；闭卷通道已证明可用。  
- **指标**：acc 可能↑；rag_worse **应↓**；hall 应↓；miss 可能略↑。

### H-B：Parametric Consistency Gate（参数一致性门）

- **机制**：更窄——先 `a0`，片段不支持/冲突则弃检索用 `a0`；约束覆盖可选。  
- **为何打 rag_worse**：直接以「是否伤害已有闭卷正确答案」为触发。  
- **指标**：acc 可能↑；rag_worse **高可能↓**。
