# 一、研究背景

当前项目研究 RAG 中的一个异常现象：

> 检索加入的信息并不总是帮助模型。
> 某些问题 Vanilla LLM 本来能够回答正确，加入网页检索结果之后，模型反而因为噪声、冗余、冲突、表面相关但不支持问题约束的信息而产生幻觉。

当前 baseline：

```text
HTML
→ sentence chunking
→ MiniLM embedding
→ query-chunk cosine similarity
→ fixed top-20
→ format_prompts
→ LLM generation
```

主要代码锚点：

```text
models/rag_llama_baseline.py
```

当前考虑的研究插入点：

```text
cosine retrieval
      ↓
【retrieval-side denoising / evidence selection】
      ↓
cleaner evidence set
      ↓
format_prompts
      ↓
LLM.generate
```

也就是说：

**只研究生成之前“给模型看什么”。**

暂时不要把主要贡献建立在：

* 修改最终 evaluator；
* 修改 ground truth；
* 生成答案后再通过 IDK/abstention 改答案；
* 单纯通过拒答增加 score；
* 人工针对测试集规则调参。

# 二、目前已经发现的关键实验现象

当前 200 条实验子集已有以下现象：

1. 存在约 25 条 `rag_worse_hallucination`：

   * Vanilla 正确；
   * 加入 RAG 后反而错误或幻觉。

2. 大量失败并不是“没有检索到相关内容”，而是：

```text
检索到了很多看起来相关的信息
→ 信息被一起塞进 context
→ LLM 被误导
→ 原本能答对的问题变错
```

3. 当前 cosine similarity 本身无法很好地区分：

   * 真正可以支持答案的 evidence；
   * 只是主题相似、实体共现、语义接近的 noise。

换言之：

```text
Semantic Relevance ≠ Evidential Utility
```

或者：

```text
“与问题相似”
≠
“对回答这个问题有帮助”
```

甚至可能出现：

```text
retrieved chunk 很相关
但它的加入对最终回答具有 negative utility
```

4. 特别典型的问题包括：

* list / set question；
* 时间约束；
* 数值约束；
* 实体约束；
* 多条件问题；
* 多网页信息拼接；
* 重复片段；
* 部分正确但不满足完整 query constraint 的句子。

例如：

```text
Question:
2017 年之后 Pixar 上映了哪些电影？

Noise evidence:
"Toy Story 4 is a Pixar film..."

这句话和 Pixar 语义高度相关，
甚至事实本身可能没有错，
但它未必严格支持当前问题的完整约束或数据集答案口径。
```

所以现在最重要的科研问题不是：

> 怎么让 cosine score 更高？

而是：

> 如何在 LLM 生成之前判断一个 retrieved evidence，或者一组 retrieved evidences，对当前问题究竟是“有帮助、无帮助还是有害”？

# 四、真正需要解决的科学问题

请围绕下面的问题进行研究级思考：

## Q1

为什么：

```text
relevance score 很高
```

仍可能是：

```text
bad evidence
```

？

---

## Q2

是否应该从：

```text
Relevance Ranking
```

转变为：

```text
Evidence Utility Estimation
```

？

即：

[
U(e,q)
======

\text{“将 evidence e 加入 context 后，对正确回答 q 的预期贡献”}
]

而不是仅仅：

[
R(e,q)
======

Similarity(e,q)
]

---

## Q3

单个 chunk 看起来都合理，但组合在一起可能产生错误。

因此是否应该把问题从：

```text
point-wise evidence scoring
```

升级为：

```text
set-level evidence selection
```

研究：

[
U(E,q)
]

而不仅是：

[
\sum_i U(e_i,q)
]

---

## Q4

是否存在：

```text
Evidence Harmfulness
```

即某段证据：

```text
单独看相关
+
事实可能正确
+
但加入 context 后使回答更差
```

？

能否预测这种 negative evidence？

---

## Q5

检索系统是否应该停止追求：

```text
retrieve as much relevant information as possible
```

而转变成：

```text
retrieve the minimum sufficient evidence
```

即：

> Minimum Sufficient Evidence Set

不预测：

```text

```


### 方向2：Evidence Harmfulness

主动识别：


### 方向3：Counterfactual Retrieval

考虑：

```text

```

---

### 方向4：Minimum Sufficient Evidence

目标不再是 top-k。

而是找到：

```text

```

---

### 方向5：Constraint-Aware Retrieval

把 query 拆成：

```text
entity
relation
time
number
set/list requirement
comparison
other constraints
```

只有真正覆盖约束的 evidence 才进入 context。

---

### 方向6：Set-level Evidence Optimization

不是逐 chunk 排名。

而是在候选集合中选择：

[
E^*=\arg\max_E U(E,q)
]

其中 utility 同时考虑：

```text
support
coverage
redundancy
conflict
harm
context budget
```

---

### 方向7：Evidence Interaction Graph

把 chunk 建成图：

```text
support
duplicate
contradict
complement
irrelevant
```

然后选择一个内部一致、覆盖完整问题约束的 evidence subgraph。

---

### 方向8：Question-Adaptive Retrieval Policy

不同问题使用不同证据策略，例如：

```text
factoid
list
set
date
number
comparison
multi-hop
```

使用不同：

```text
context size
selection criterion
redundancy tolerance
conflict policy
```

---

### 方向9：Retrieval Negative Learning

利用已有：

```text
Vanilla correct
RAG wrong
```

样本作为一种特殊监督信号。

研究是否能学习：

```text
哪些 retrieved evidence pattern 容易伤害模型
```

注意：

绝不能在测试时使用 GT。

---

### 方向10：Evidence Bottleneck

把 RAG 看成一个信息瓶颈问题：

```text
Candidate Evidence
      ↓
Evidence Bottleneck
      ↓
Minimum useful information
      ↓
Generator
```

探索：

> 少而完整的信息是否优于多而相关的信息？

# 十四、额外要求：寻找“真正值得做”的突破口

特别认真思考以下这个可能的研究转向：

传统 retrieval：

[
\text{score}(q,e)=Similarity(q,e)
]

我们真正需要的可能是：

[
\text{score}(q,e)
=================

ExpectedAnswerUtility(e|q)
]

甚至：

[
\text{score}(q,e,E)
===================

MarginalUtility(e|E,q)
]

即：

> 一个 evidence 是否应该被加入，不只取决于它自身是否相关，还取决于当前已经选择了哪些 evidence，以及它加入后是否真正增加回答问题所需的信息。

进一步考虑：

[
\Delta U
========

U(E\cup e,q)-U(E,q)
]

当：

```text
ΔU > 0
```

加入 evidence。

当：

```text
ΔU ≈ 0
```

它可能只是 redundancy。

当：

```text
ΔU < 0
```

它可能就是 harmful evidence。

请判断：

**这个 formulation 是否值得发展成为本项目真正的方法创新核心。**

不要默认答案是“值得”。

要求正反双方充分辩论。
