# 2026-08-27 · 本项目的 RAG 实现，为什么能称为 RAG？

> 来源：Cursor 讨论整理  
> 关联：`models/rag_llama_baseline.py`、`models/vanilla_llama_baseline.py`、[07-Task与基线关系说明.md](../07-Task与基线关系说明.md)

---

## 1. RAG 是什么

**RAG** = **Retrieval-Augmented Generation（检索增强生成）**：

1. **Retrieval**：从外部语料中检索与问题相关的片段  
2. **Augmented Generation**：把这些片段作为上下文，交给 LLM 生成答案  

本项目的 `RAGModel` 正是这条 **retrieve → augment prompt → generate** 流水线；`InstructModel`（Vanilla）则跳过检索，形成闭卷对照。

---

## 2. 本项目 RAG 的两步

```
问题 query ──→ 检索 ──→ Top-20 相关句子 ──→ Llama 生成答案
                ↑
search_results（网页 HTML，数据集预置）
```

### 2.1 Retrieval（检索）

数据里每条样本带有 `search_results`（最多 5 页完整 HTML，CRAG 已预先「搜好」）。`RAGModel` 会：

1. **切块**：HTML → BeautifulSoup 抽文本 → 按句切分（`ChunkExtractor`）
2. **向量化**：`all-MiniLM-L6-v2` 对问题和句子分别编码
3. **召回**：在同一题的 chunks 内算余弦相似度，取 Top-20 句（`NUM_CONTEXT_SENTENCES=20`）

代码位置：`models/rag_llama_baseline.py` — `extract_chunks` → `calculate_embeddings` → 余弦相似度 `argsort` 取 top-N。

### 2.2 Augmented Generation（增强生成）

检索到的句子写入 prompt 的 **References**，再让 Llama 基于引用作答：

- system：要求只用 references 回答，不够则 `I don't know`
- user：`# References` + 句子列表 + `Question` + `Current Time`
- 最后 `self.llm.generate(...)`

代码位置：`format_prompts()` → `llm.generate()`。

---

## 3. 与 Vanilla 的对比（为何能叫 RAG）

| | **Vanilla** (`InstructModel`) | **RAG** (`RAGModel`) |
|--|-------------------------------|----------------------|
| 是否用 `search_results` | ❌ 忽略 | ✅ 解析 → 检索 → 注入 prompt |
| 知识来源 | 模型参数（闭卷） | 外部检索片段 + 模型 |
| prompt 里有没有 References | 无 | 有 Top-20 句子 |

Vanilla 的 `format_prommpts()` 只有 `Current Time` + `Question`；RAG 多了检索到的 References。这是 RAG 与闭卷 LLM 的核心区别。

---

## 4. 常见误解

### 4.1 「没有实时联网搜索，还算 RAG 吗？」

**算。** RAG 的定义是「生成时利用外部检索到的文本」，不要求推理阶段再调搜索引擎。CRAG 把网页结果**预先放进数据集**；基线在**这批语料上做向量检索**，仍是标准 retrieve-then-generate。

### 4.2 「实现很朴素，还算 RAG 吗？」

**算，只是演示基线。** 代码注释写明未调优（`NOT been tuned for performance`）。没有重排序、混合检索、多轮检索等，但仍是经典 RAG：**稠密向量检索 + 拼进 context + LLM 生成**。论文 Table 里的 naive web-augmented 也是类似思路。

### 4.3 「和 RAGFlow 那种比呢？」

RAGFlow 是完整产品（解析、分块、索引、工作流）。本项目是**竞赛最小可跑通基线**，只覆盖 RAG 核心环，不含工程化组件。

### 4.4 「RAG-KG 又是什么？」

`RAG_KG_Model` 在网页 RAG 之上再调 Mock API 查 KG，是 **RAG + 结构化检索**；`RAGModel` 只用网页，对应 Task 1 的网页 RAG 设定。

---

## 5. 与已跑实验的关系

Vanilla vs RAG 全量（2706，DeepSeek 裁判）：

| 指标 | Vanilla | RAG |
|------|---------|-----|
| accuracy | ~15.8% | ~23.1% |
| missing | ~68.3% | ~55.1% |
| hallucination | ~16.0% | ~21.8% |

检索确实在起作用（答对更多、拒答更少），说明是在做 RAG，而不只是改了 prompt 措辞。主矛盾从「不会答」转向「答得更猛、也更容易编」——与「证据不足拒答」研究方向一致。

---

## 6. 结论（一句话）

本项目 RAG 能称为 RAG，是因为它实现了 **「从 `search_results` 检索相关片段 → 写入 References → LLM 条件生成」**；朴素、离线语料、无实时搜索，都不改变这个定义。研究方向应落在 RAG 链路的 **检索质量 / 证据是否足以支撑回答** 环节。
